# Assumptions & Decisions

Two registers. **Assumptions** are things this specification takes as true in the absence of a
decision — if an assumption is wrong, the linked work changes. **Decisions** are choices already made
and recorded, with the reasoning kept so they can be revisited honestly.

Open questions live separately in [80-open-questions.md](../80-open-questions.md).

## 2. Decisions

| ID | Decision | Alternatives considered | Rationale |
| --- | --- | --- | --- |
| **DEC-01** | **Modular monolith** for the write-side domain (customers, trades, wallet, invoicing) deployed as two API hosts plus one worker host, rather than fine-grained microservices | Microservice per bounded context | The domain is small, the team is small, and the hardest problems are transactional (wallet + trade state) rather than scale. Aspire makes the multi-host layout cheap to run locally. Microservices can be extracted later along the module seams. |
| **DEC-02** | **Separate APIs for the customer portal and the employee portal**, sharing a domain library | One API with role-based routing | Different auth realms, different exposure (one is public-facing), different rate-limit and hardening profiles. Cheap to do with a shared library; expensive to retrofit. |
| **DEC-03** | **Ingestion is decoupled from processing.** The PVNed webhook persists the raw payload, acknowledges, and enqueues | Parse and process synchronously in the request | PVNed retries on non-2xx. Slow parsing would cause duplicate deliveries. Raw retention also makes replay and dispute resolution possible. |
| **DEC-04** | **Append-only ledger with derived balances**, with a materialised balance row per wallet updated in the same transaction | Balance column only; or event-sourcing the whole domain | Gives an auditable history and O(1) balance reads. Full event sourcing is more machinery than this domain needs. |
| **DEC-05** | **Reservations are ledger-visible but do not change the settled balance.** Each entry records deltas to both settled and reserved amounts, and stores all three resulting balances | Reservations in a side table only | The brief asks for reserved funds to appear as ledger lines with a resulting balance. This satisfies it without double-counting. |
| **DEC-06** | **Trade state changes are events, not column updates.** The current state is a projection of an append-only `trade_event` stream | Status column with an audit trigger | The audit trail is a first-class product requirement ("visible both by customer and employee"), not an afterthought. |
| **DEC-07** | **Interval data is stored per version, with a pointer to the current version per (metering point, delivery date, direction)** | Overwrite on each new document | PVNed sends corrections for up to 10 working days and never revises a document. Keeping versions makes "what did we invoice on" answerable. |
| **DEC-08** | **All timestamps stored as `timestamptz` (UTC); all business days computed in `Europe/Amsterdam`** | Local time storage | The only way DST arithmetic stays sane. Interval position ↔ timestamp conversion is centralised in one calendar service. |
| **DEC-09** | **PostgreSQL only** — no separate time-series database in the first track | TimescaleDB, InfluxDB, ClickHouse | Volume is modest: a 50-EAN customer generates ~3.5 M rows/year. Native declarative partitioning by month plus a BRIN/btree index handles it. Revisit if EAN count reaches four digits. |
| **DEC-10** | **Hangfire with PostgreSQL storage** for scheduled and background work | Azure Functions, Quartz.NET, a hosted queue | Stated preference; keeps the local Aspire story simple; dashboard is useful operationally. |
| **DEC-11** | **Public website is a separate Angular application**, not a route inside the customer portal | Route in the customer portal | Different audience, different caching and SEO needs, and it must stay up when the portal is in maintenance. |
| **DEC-12** | **Money is `numeric(18,6)` in the database, rounded to 2 decimals only at presentation and invoice-line level** | `numeric(18,2)` throughout | Unit prices are €/MWh with sub-cent precision, and volumes are fractional. Rounding early loses money in aggregate. |
| **DEC-13** | **The offer countdown is authoritative on the server.** The client renders a timer; expiry is decided by a server-side job and by a guard on every accept attempt | Client-side expiry | Clock skew and tab-sleep make client timers unsafe for a financially binding window. |
| **DEC-14** | **Peak-hour definition is reference data, not code.** A named calendar per commodity and year, with the working-day rule and the holiday list as data | Hard-coded Mon–Fri 08:00–20:00 | [OQ-02] was unresolved when this was taken, and even now that **[DEC-19]** has settled it the holiday list could change. Making it data means the answer can change without a release. The list is currently **empty** — the mechanism stays, it simply excludes nothing. |
| **DEC-15** | **Gas is modelled as a discriminator from day one** (`commodity` on metering point, product, tariff and price) but no gas logic is implemented | Electricity-only model, migrate later | The column is nearly free now; retrofitting a commodity dimension across interval data, blocks and invoices is not. |
| **DEC-16** | **A customer is a company with one or more accounts, and all accounts of a company have identical privileges.** Accounts are created and deactivated by PeakPower employees only | An intra-company role model (viewer / trader / approver); customer self-service account management | Confirmed by the stakeholder. The customer decides internally who is allowed to do what; encoding their internal governance in the platform would mean maintaining someone else's org chart. The platform's job is to record precisely who acted — which is what makes **[DEC-17]** the necessary counterpart. Closes [OQ-04]. |
| **DEC-17** | **Every customer-initiated action records the acting account**, not merely the company. Trade events, wallet movements and audit records all carry account id, display name and job title | Company-level attribution only | Direct consequence of **[DEC-16]**: if every account can spend the company's money, "the company accepted the offer" is not an adequate record. It also makes the normal split — one person spots the exposure, another approves the spend — legible instead of anonymous. |
| **DEC-18** | **A trade may be started by one account and answered by another.** No requirement that the accepting account is the requesting account | Locking a trade to its originator | The realistic workflow. An energy manager raises the request at 14:25 and the finance director accepts at 14:44; forcing the originator to accept would push customers back to phone calls, which is the behaviour this platform exists to replace. |

### Decisions taken 2026-08-11 — the eleven blocking open questions

These eleven closed the P1 set in [80-open-questions.md](../80-open-questions.md). Several are scoped to a
proof of concept; where that is so, the decision says what the PoC does **and** what must still be built
structurally now so the deferred part drops in later. A PoC decision that quietly hardens into v1 is the
failure mode these notes exist to prevent.

| ID | Decision | Alternatives considered | Rationale & consequences |
| --- | --- | --- | --- |
| **DEC-19** | **Peak = Monday to Friday, at or after 08:00 and strictly before 20:00, Europe/Amsterdam. Public holidays are *not* excluded** — a holiday falling on a weekday is a peak day. The peak calendar's `excluded_dates[]` is empty | Excluding the Dutch public-holiday list, which would need an owner and an annual update | Matches the exchange convention for Dutch power peak-load products, so PeakPower's peak volume agrees with the market it hedges in. Closes [OQ-02] and **retires risk R-03** (~3.5% of annual peak volume, previously the third-highest risk). **[DEC-14] still stands** — the calendar remains reference data with a weekday rule and an exclusion list; the list is simply empty, so the answer can still change without a release. |
| **DEC-20** | **The proof of concept runs with no authentication. The production identity provider is Microsoft Entra ID** | Authentik (self-hosted), Okta/Auth0 | Closes [OQ-03], and effectively answers [OQ-73] — Entra only makes sense against an existing Microsoft tenancy. ⚠ **Skipping authentication is not skipping tenancy.** The `customer_id` / `account_id` context pipeline must be built now, fed by a development context provider, so the EF Core global query filter, row-level security and the 404-not-403 behaviour are exercised from the first commit. Retrofitting tenancy isolation into a system that never had it is how [R-06] happens. Note Entra's `customer_id` claim mapping is the fiddliest part of that provider — spike it before Phase 1 ends. |
| **DEC-21** | **The PoC ingests generated data in the PVNed document format. A mock PVNed service follows in the test environment; the real integration is validated later** | Waiting for a PVNed test environment before building ingestion | Unblocks Phase 1 without a vendor dependency. Closes [OQ-05] *for the PoC only*. ⚠ **Risk R-01 (score 20) is deferred, not closed** — the real endpoint, auth mechanism, ack format, retry behaviour and the nine documentation inconsistencies ([OQ-65]) remain unvalidated, and the register's warning that PVNed may not offer a usable test environment still stands. Mitigation: generate the fake data **against the reconstructed sample message and XSD in [PVNed timeseries](../30-integrations/01-pvned-timeseries.md)**, and drive it through the real webhook, parser and validation path — not through a shortcut that bypasses them. Fake data that skips the parser proves nothing. |
| **DEC-22** | **Production nets against consumption.** The platform's volume basis is **net usage** = consumption − production, per interval per metering point | Consumption-only (the previous [AS-06]); production as display-only insight | Closes [OQ-11] and **supersedes [AS-06]**. Consequences: coverage and the net position are measured against net usage, not gross consumption; **net usage may be negative in an interval** when production exceeds consumption, which is treated as export and settled under **[DEC-23]**; the energiebelasting basis becomes net, which finally makes the platform agree with [AS-14] instead of contradicting it; the consumption chart must show net alongside the two gross series. The register graded this assumption's blast radius *large* — treat [Position & coverage](../50-calculations/02-position-and-coverage.md) and [Invoice calculation](../50-calculations/03-invoice-calculation.md) as changed, not merely annotated. |
| **DEC-23** | **Surplus (over-covered) volume is credited at the day-ahead price** for the interval concerned | Settling surplus at the block price; not settling it at all and letting PeakPower keep the difference | Closes [OQ-13]. Symmetric with the treatment of uncovered volume, which keeps the position maths in one shape rather than two. Appears on the invoice as a **separate sale line, never netted against purchase lines** — uncovered and surplus volumes occur at different times and therefore at different prices. Also covers the negative net usage introduced by **[DEC-22]**. |
| **DEC-24** | **Energiebelasting is out of scope for now.** Invoice line 5 is not implemented | Implementing EB against a provisional tariff table | Closes [OQ-14] *by deferral*. ⚠ **Two consequences that must not be lost.** First, the January **annual true-up loses its principal reason to exist** — tier crossings were the point — so it is deferred alongside EB, retaining only its residual role of correcting late metering data. Second, **EB is a legal obligation, not a feature**: this must be reopened before a single invoice is issued to a real customer. Keep `IEnergyTaxCalculator` and the `billing.energy_tax_tariff` table in the model, unpopulated, so the calculation drops in rather than being retrofitted through the invoice engine. |
| **DEC-25** | **Imbalance is out of scope.** Invoice line 3 is not implemented; PVNed `A12` documents are stored but not turned into charges | Pro-rata allocation on consumption behind a policy interface | Closes [OQ-15], and moots [AS-18] and the allocation-key question with it. Removes the requirement to state an allocation method in the customer contract. The volume identity check simplifies accordingly — see [Invoice calculation](../50-calculations/03-invoice-calculation.md). Storing `A12` rather than discarding it keeps the option open at the cost of a table. |
| **DEC-26** | **All prices, wallet balances and reservations are VAT-exclusive.** VAT is added at invoice level | VAT-inclusive wallet amounts | Closes the inclusive/exclusive half of [OQ-17] and **confirms [AS-10]** — the reservation is the trade value ex-VAT. ⚠ **Two sub-questions remain open and both are money-affecting.** (a) The **rate per line category**, plus any exemptions or reverse-charge cases — 21% NL standard is assumed until confirmed. (b) Whether the wallet `INVOICE_DEBIT` settles the VAT-**exclusive** subtotal or the VAT-**inclusive** total. If it is the inclusive total, a reservation sized ex-VAT under-covers the eventual debit by the VAT rate — which is precisely the exposure [AS-10] was flagged for. Resolve before wallet settlement is built. |
| **DEC-27** | **Montel price indications must not be displayed publicly.** Display inside the authenticated portal is permitted | Public price teaser on the marketing site; unrestricted customer export | Closes [OQ-24] and **retires the public-price element of [F14]**. ⚠ **Customer export (CSV) is not covered by this answer** — treat it as not permitted until the Montel licence says otherwise, since export is redistribution. Risk R-07 is reduced but not closed: F04 keeps its "Indication — not an offer" labelling and its stale-data flagging regardless. |
| **DEC-28** | **The client-money question is deferred.** No segregated client account, no regulatory analysis, for now | Obtaining legal advice before building the wallet | Closes [OQ-31] *by deferral*. ⚠ **This is a go-live gate, not a build gate.** The PoC must not hold real customer funds — the wallet may be exercised with test money only. Risk R-05 (score 15) stays open on the register and must be answered before any real deposit is accepted, because an adverse answer may imply a licence application with its own lead time. |
| **DEC-29** | **The identity provider owns credentials for all normal access. The platform never stores a customer password**, and the PoC has no authentication at all. ⚠ **Amended 2026-08-11 by [DEC-53]** — a narrowly scoped break-glass password path now exists for named employee accounts | The platform holding username and password itself | Closes [OQ-78]. Phase 1 does not build credential storage, reset flows or lockout policy **for customers**. Consistent with **[DEC-20]**: Entra ID owns the credential, the platform owns the `customer_id` ↔ `account_id` mapping and validates the claim pair on every request. Read together with **[DEC-53]**, which carves out the break-glass exception and states its constraints. |

### Decisions taken 2026-08-11 (second round) — the P2/P3 queue

Thirty-six further questions were decided. Thirty-five more were **reviewed and consciously parked** —
they remain open in [80-open-questions.md](../80-open-questions.md), marked as deliberately deferred
rather than overlooked. [OQ-07] was not reached.

Three of these decisions **change work already specified** rather than merely filling a gap:
**[DEC-35]** moves the surcharge to €/kWh, **[DEC-44]** adds a sixth invoice line category, and
**[DEC-33]** adds a state to the trade state machine. Those three are the expensive ones.

| ID | Decision | Consequences |
| --- | --- | --- |
| **DEC-30** | **Gas keeps the same EAN model and the same block products** when it enters scope. Only pricing and units differ — volumes in **m³** rather than kWh | Answers [OQ-01]. Vindicates **[DEC-15]**: the commodity discriminator is the whole of the structural work. ⚠ Gas is metered in m³ but conventionally *billed* on energy content — whether the platform must apply a **calorific correction** (m³ → kWh) is not answered here and should be settled before gas is built |
| **DEC-31** | **EANs are not validated against an external market register.** The GS1 check digit remains the only validation | Answers [OQ-06]. Typos that pass the check digit reach ingestion and surface as quarantined unknown-EAN documents — an acceptable trade for not taking an EDSN/C-AR dependency |
| **DEC-32** | **Minimum requested volume 0,1 MW, increment 0,1 MW** | Answers [OQ-08]. ⚠ Coarser than the 0,001 MW increment the specs assumed. Every requested volume is now a multiple of 0,1 MW, so per-EAN allocations are too — which makes the "non-whole-MW total" warning in [F05](../10-features/F05-energy-block-trading.md) fire far more often, since 0,1 MW steps rarely sum to whole clips |
| **DEC-33** | **Four-eyes approval is required above a value threshold** | Answers [OQ-09] — and is the one answer that **adds a state to the trade state machine**, which was previously exactly ten transitions. Needs an approval state, an approver identity distinct from the acceptor, and back-office UI. ⚠ **The threshold value is not specified.** It must be reference data, not a constant, and it must be set before the state is built |
| **DEC-34** | **Short selling is not permitted.** A customer may not sell a block they do not hold | Answers [OQ-10] and confirms the default. Removes the need for an authorisation flag and a credit view. Sell requests validate against confirmed holdings for the period |
| **DEC-35** | **The surcharge is a per-unit fee quoted and stored in €/kWh**, not a fixed periodic fee or a scheduled deposit | Answers [OQ-12] and settles the nature question. ⚠ **This is a unit change, not a label change.** Every other price in the system is €/MWh. Two consequences: the surcharge formula loses its `/1000` divisor, and the rate column needs **widened precision** — €/kWh at 4 decimals is 1000× coarser than €/MWh at 4 decimals. See [Invoice calculation](../50-calculations/03-invoice-calculation.md) |
| **DEC-36** | **The NL day-ahead curve arrives at 18:00 Amsterdam time** for electricity | Answers [OQ-16] in part. Replaces the four-attempt 13:00/14:00/15:00/18:00 schedule with a single scheduled fetch plus retry. ⚠ Does **not** answer the resolution Montel delivers, nor whether history is available for backfill — both still needed, and backfill depth limits how far back positions can settle |
| **DEC-37** | **Network and transport costs (netbeheerkosten) are out of scope.** The DSO bills grootverbruik customers directly | Answers [OQ-18], confirming the working assumption |
| **DEC-38** | **PVNed sends one document per EAN per day** | Answers [OQ-21]. Sizes ingestion at roughly one document per metering point per day rather than a daily batch — which raises document count but keeps each payload small and makes the per-(point, date) mutex in [Background jobs](../20-architecture/06-background-jobs.md) the natural unit of concurrency |
| **DEC-39** | **The charting library must be open-source and free**, or written in-house | Answers [OQ-22] by excluding commercial licences. Keeps the phase-0 spike, but narrows it to the free field and to the cost of building custom. "The chart is the product", so this constrains the most user-visible part of the platform |
| **DEC-40** | **A metering point must be valid for the entire delivery period** to be included in a trade | Answers [OQ-26]. Removes pro-rated allocations from the model entirely — a simplification worth having. Validation rejects the request rather than silently trimming |
| **DEC-41** | **The pre-submission wallet check uses 100% of the estimate, with no buffer** | Answers [OQ-27], confirming the default. ⚠ Interacts with [OQ-83]: if the eventual invoice debit turns out to be VAT-inclusive, the absence of a buffer is what makes the shortfall bite |
| **DEC-42** | **A customer may only buy into delivery periods that have not yet started** | Answers [OQ-28]. Removes partial-period volume and mid-period coverage starts from the model. Combined with **[DEC-40]**, every block covers a whole period at a constant MW — which is what keeps the interval maths simple |
| **DEC-43** | **There is no refund payout path. Surplus wallet balance stays in the wallet** | Answers [OQ-30]. Removes the refund flow, the approval question and the provider-versus-manual-transfer question. ⚠ **Offboarding is left unanswered**: a customer closing their account with a positive balance has no route for their money. The specs flagged this as needed before go-live; it is now a known gap rather than an open question, and interacts with [OQ-29] |
| **DEC-44** | **Feed-in is its own invoice line category, settled at a feed-in tariff** — not at the day-ahead price | Answers [OQ-35] on both halves: day-ahead settlement uses the **raw** price with no spread, and physically exported volume is separated out. ⚠ **This partially reopens [DEC-23].** The sale leg now splits: *unused block cover* still settles at day-ahead per [DEC-23]; *physical export* settles at the feed-in tariff. New line category, new per-customer reference-data table alongside the surcharge, and a changed volume identity. See [Invoice calculation](../50-calculations/03-invoice-calculation.md) |
| **DEC-45** | **The platform owns invoice numbering** | Answers [OQ-37], adopting the recommendation. Gapless sequential numbering per legal entity per year stays a platform responsibility, so the customer experience does not depend on an integration that will occasionally fail |
| **DEC-46** | **The platform generates the invoice PDF** | Answers [OQ-38]. Keeps branding and the portal download path under platform control, and means Odoo receives structured data rather than owning the customer-facing document |
| **DEC-47** | **Invoices are both emailed to the customer and available in the portal** | Answers [OQ-39]. Raises deliverability from a convenience to a requirement — see **[DEC-48]** |
| **DEC-48** | **SendGrid is the transactional email provider** | Answers [OQ-40]. ⚠ A dedicated sending domain with SPF, DKIM and DMARC is still required and is a lead-time item: offer notifications are time-critical, and **[DEC-47]** now puts invoices on the same channel |
| **DEC-49** | **Wallet warning and critical thresholds are fixed amounts**, not derived from trading volume | Answers [OQ-41]. Simple and predictable; less useful at the extremes of customer size, which is the trade accepted |
| **DEC-50** | **The trade desk needs no real-time collaboration beyond a soft lock — but must warn when two customers request the same period** | Answers [OQ-42], and adds a requirement rather than only removing one. The warning is a desk-side signal that concentration is building in one period |

Moves a security control out of the platform's control surface, which is worth recording explicitly |
| **DEC-52** | **No customer-managed encryption keys.** Platform-managed keys at rest | Answers [OQ-59] |

An unrehearsed break-glass path is not a break-glass path. Customers remain fully provider-authenticated |
| **DEC-54** | **Angular 22** for all three front-end applications | Answers [OQ-49] on the framework version. ⚠ Does **not** answer the component-library half of [OQ-49]; combined with **[DEC-39]**, expect the free field there too |
